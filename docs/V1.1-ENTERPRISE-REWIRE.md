# v1.1 – Enterprise rewire (SSO, OIDC, IRSA)

## What changed
| Area | v1.0 | v1.1 |
|---|---|---|
| Terraform CI auth | Static AWS keys | GitHub OIDC roles (`terraform_plan` read-only, `terraform_apply` main-only) |
| ECR push | OIDC (any branch of repo) | OIDC, trust limited to main/develop/release/* |
| Human cluster access | Creator admin | EKS access entries for IAM Identity Center (SSO) admin/readonly roles |
| CI → gitops repo | Personal PAT | GitHub App short-lived token (`actions/create-github-app-token`) |
| Argo CD → gitops repo | PAT | GitHub App credentials |
| In-cluster AWS access | IRSA | IRSA (unchanged) |
| Actions | floating tags | pinned to commit SHAs, Dependabot keeps them fresh |
| Trivy | `exit-code 0`, `@master` | pinned, fails on CRITICAL/HIGH |
| Terraform CI | none | Trivy IaC scan job |
| Org name | zenpharma | mackllc |

## Bootstrap order
1. Local admin `terraform apply` (creates OIDC roles + SSO access entries; set `sso_admin_role_arn`, `sso_readonly_role_arn`; optionally `enable_cluster_creator_admin=false`). SSO role ARNs omit the `aws-reserved/sso.amazonaws.com/<region>/` path.
2. Set repo variables in infra: `AWS_TF_PLAN_ROLE_ARN`, `AWS_TF_APPLY_ROLE_ARN` (see terraform outputs).
3. Create a GitHub App (Contents: read/write + Pull requests: write on `gitops`). Install on gitops.
   - backend/frontend: variable `GITOPS_APP_ID`, secret `GITOPS_APP_PRIVATE_KEY`.
   - Run `scripts/02_bootstrap_argocd.py` and enter app ID, installation ID, .pem path (needs read-only on gitops).
4. Remove old secrets: `GITOPS_TOKEN`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`.
5. Argo CD SSO: configure `dex.config` in `argocd-cm` with the GitHub or OIDC connector, map groups in `argocd-rbac-cm`, then disable the local `admin` user.

## IAM model (no IAM users)
- **People:** IAM Identity Center (SSO) only, short-lived credentials, mapped to EKS via access entries.
- **CI/CD:** GitHub OIDC -> `sts:AssumeRoleWithWebIdentity` (ecr-push, terraform-plan, terraform-apply).
- **Pods:** IRSA. Each microservice gets exactly 1 role, 1 trust policy, 1 permission boundary, 1 permission policy, created by one module (`modules/irsa-role`).
- **Argo CD:** one role each for `dev`, `qa`, `prod`. Helm runs inside Argo CD (repo-server/controller), so it inherits that identity; there is no separate Helm role.
- **Guard:** CI fails if any `aws_iam_user`/`aws_iam_access_key` resource appears. Every boundary also denies creating IAM users/keys/login profiles.

### Naming convention: `<project>-<env>-<component>-<type>`
| Type | Suffix | Example |
|---|---|---|
| IRSA role | `-irsa` | `pharma-dev-auth-service-irsa` |
| Permission policy | `-policy` | `pharma-dev-auth-service-policy` |
| Permission boundary | `-boundary` | `pharma-dev-auth-service-boundary` |
| GitHub OIDC role | `-gha` | `pharma-dev-ecr-push-gha`, `pharma-dev-terraform-apply-gha` |

Service account name == component name. Gitops values carry `<ACCOUNT_ID>` placeholders in the role-arn annotation; replace with your account ID (or use `terraform output microservice_role_arns`).

### Production topology note
This repo uses one cluster and one OIDC provider for a portfolio demo. In a real setup, qa and prod each get their own cluster, OIDC provider and AWS account, and `envs/qa` / `envs/prod` call the same `modules/iam` with their own provider ARN.

## Database credentials (RDS-managed, auto-rotated)

- RDS owns the master password (`manage_master_user_password = true`) with rotation every 7 days.
  The password never appears in Git, tfvars, CI secrets or Terraform state.
- `/pharma/<env>/db-config` in Secrets Manager holds only the non-secret host.
- ESO reads username/password from the RDS-managed secret (`terraform output rds_master_secret_arn`)
  and the host from `db-config`, refreshing every 15 minutes.
- Apps read the password at startup, so pods must be restarted after a rotation
  (future improvement: Stakater Reloader).
- Future improvement: RDS IAM auth (needs JDBC wrapper changes in the Java services).
